# Specification-driven ES (12 Nov 2026)

One file, `config/teams/fig_re/es_spec.yaml`, describes the FIG Executive Summary part by part. It drives four things, so they cannot drift apart:

1. **The Word template.** `scripts/build_template_fig_v1.py` lays out `templates/ES_Template_FIG_v1.0.docx` from the specification and writes the matching mapping to `config/teams/fig_re/template.yaml`. The package shell (styles, header, footer, page set-up) comes from the owner's v0.2 file, which is only read.
2. **Drafting.** The model is asked for exactly the parts marked `model` or `extract`, in the JSON shape the specification implies.
3. **Export.** Each part is found in the template by its table header or guidance placeholder and filled from the saved draft.
4. **The screen.** The workbench shows each section's parts in template order (`GET /cases/{id}/es-spec`).

The first-generation path (team `fig`, template v0.3, mock wording, 569 tests) is unchanged and remains the offline regression case. The new path is team `fig_re`, which reuses `fig`'s catalogue, rules, dependencies, workflow, analytics and prompts through `config/teams/fig_re/extends.txt`.

## Who fills what

| `fill` | Filled by | Rule |
|---|---|---|
| `model` | Drafting model | Every paragraph, row and answer cites a source page. Figures in wording must appear on a cited page (compared by value, never rounded). |
| `extract` | Model copies, Python checks | Each figure comes with the exact source line. Python confirms the line is on the cited page and contains the figure, converts the unit, and computes change, share, totals and ratio columns. |
| `python` | Code only | Tables computed from the structured workbooks (rent roll, financial projections) and from figures already checked: key tenants, lease expiry, debt service, base case, stress cases, assumptions, headroom. |
| `case`, `ca`, `workflow` | Case set-up, the analyst, the approval workflow | For example the recommendation box and sign-off. |
| `asset` | Saved files | Photographs and the location map declared in the case's `case.yaml`; the ownership chart is drawn by Python from the checked unitholders table. |

Anything that fails a check is withheld and listed as a gap. Nothing is repaired by guessing. Parts marked `only_when: existing_client` state "Not applicable: new to bank" for a new borrower. For a new-to-bank borrower, existing limits and outstanding amounts are entered as nil by code.

Code: `backend/app/es2/` (`spec.py`, `drafting.py`, `numbers.py`, `compute.py`, `export.py`, `api.py`). `DraftingService.generate` and `ExportService.prepare` hand over to it when the case's team has a specification.

## Live calls and cost

- Route: Claude direct to Anthropic, model `claude-fable-5-2` (`config/models.yaml`, entry `fable-5-2-direct`). No other live route is enabled.
- Gate: a live call needs all of: the process started with `WB_CREDIT_LIVE=1`, the registry entry enabled, and its key in the environment or `.env`. Tests and the mock demo never set the flag, so the screens cannot trigger a paid call there.
- Every call is appended to `runtime/costs/ledger.jsonl` with model, route, case, section, purpose, tokens, cost and duration, including failed calls. `GET /costs` returns running totals by model; `docs/cost_log.md` is regenerated by the live run script.
- Cost uses the usage the provider reports and the published rates held in the registry entry (USD 8 input and USD 40 output per million tokens, price date 3 Nov 2026). A call served by a fallback model is recorded as unpriced.
- Large sections are drafted in more than one request (six parts each) so a response does not hit the output limit.

## Limits

- Not the bank's real template. It follows the 14 section names and the owner's v0.2 edits, laid out to common credit paper practice.
- The Credit Assistant chat still uses the first-generation mock operations; live rewording and question answering are not built.
- Rebuilding the template changes its bytes. A saved case pins the template version it was drafted on, so redraft after a rebuild (the live run with `--fresh` does this).
- Page selection for long documents is by keyword. A figure on a page that was not selected shows as "Not provided" rather than being guessed.
- The ownership chart shows the top three unitholders from the checked table; deemed interests can overlap.
- Photograph licences are as shown on Wikimedia Commons on the retrieval date; OneMap terms were not reviewed in detail. Check both before any use outside this prototype.

## Analyst added content (13 Nov 2026)

The analyst can add content anywhere in a specification-driven section: typed text, a table pasted from Excel or Word, or a screenshot (PNG or JPEG, up to 8 MB). On the screen, each part of a section has an "Add text, a table or a screenshot here" control.

- A block is kept exactly as added. The system does not check, recalculate or reword it, and it is labelled "Analyst added. Not checked by the system." on the screen and in the Word ES.
- Each block follows a part of the section (or sits at the top). It can be moved up or down, edited (text and title) or removed.
- Every change is a new version of the section, and resets the section's confirmation. The drafted wording, tables and sources are untouched.
- A redraft keeps the blocks and the accepted assistant notes of the version it replaces.
- The Word export places each block after the part it follows. A block whose part no longer exists in the specification is placed at the end of the section, so a template change does not lose it.
- Sections that read another section (11 and 14) read its added text and tables too.
- Limits: 30 blocks per section, 80 rows and 14 columns per table. Tables are plain grids: merged cells and cell formatting are not kept. The first-generation path (team `fig`) does not have this.

Code: `backend/app/es2/blocks.py`, `POST /cases/{id}/sections/{n}/blocks`, `GET /cases/{id}/blocks/{name}`, `frontend/src/workbench/Blocks.jsx` and `paste.js`.

## Sections marked for update (13 Nov 2026)

A draft pins what it read from other sections: the wording of sections named in `uses_sections`, and the computed parts read by Python tables (section 10's headroom table reads the loan to value line of section 8). When that content changes, the reading section is marked "Update required" and its wording is kept. A new version of the other section with the same content, such as an added note, does not mark it. Drafts saved before this change carry no pins and gain them at their next redraft.

## Model sense check (13 Nov 2026)

Python computes some tables and checks every copied figure against its source line. Two kinds of table are outside those checks as a whole: tables the model drafts from cited sources, and tables the analyst adds. The sense check asks the case's model to read those tables in one section and say what does not look reasonable: totals that do not add up, a wrong unit or sign, dates out of order, a figure that disagrees with another row or with the tables Python computed anywhere in the ES.

- Run it with "Sense check" on a section, or for the saved live case with `scripts/demo/live_run.py --sense [--sections N ...] [--cap USD]`.
- Each finding is shown under its table as "Suggested check", with the row marked. It is a prompt for a person. It never changes a value and never blocks an action. A table with no finding is not verified by this, and the screen says so.
- Python keeps only findings that point at a table and row that were sent, drops any whose wording reads as an assurance or a decision, and keeps at most eight per section.
- The analyst can mark a suggestion as looked at, with a note. Suggestions not yet looked at are listed in the Word ES under "Open items for the credit analyst".
- A check belongs to one version of the section. After the section changes it is shown as out of date and leaves the export list.
- It is a live model call: it needs the live gate, and every call is recorded in the cost ledger with purpose `sense_check`. A section costs about USD 0.05 to 0.50. The whole Keppel ES cost USD 1.63.
- Limits: it reads one section's tables at a time against the computed tables; it does not open source documents, so it cannot say which of two disagreeing figures is right.

Code: `backend/app/es2/sense.py`, `GET /cases/{id}/sense-checks`, `POST /cases/{id}/sections/{n}/sense-check`, `POST /cases/{id}/sense-checks/{check}/resolve`.

## Papers list (13 Nov 2026)

One store can hold several papers. `GET /papers` lists each with its stage, who it is waiting for, drafting progress, sections to update or returned, inputs outstanding and model suggestions not yet looked at. The Papers screen (`#/papers`) shows the list with filters (all, waiting for me, with others); opening a paper switches the whole workbench to it, and the top bar has a paper switcher. ## Maker and checker (13 Nov 2026)

The top bar has a role switch: credit analyst (maker) or Credit Head (checker). It is a demo switch, not a login; each role acts under a fixed demo name. The workflow rules were already in the back end (`backend/app/services/workflow.py`); this adds the screens and the checker's section marks.

- **Maker.** The Review page lists what must be true before submission: every section confirmed or not applicable, and a recorded reason for each required input that is not complete. Model suggestions not yet looked at are shown but do not stop the submission. Submitting records the exact version of every section and locks the ES.
- **Checker.** Reads each section with its sources and marks it reviewed or raises a query with a note. The Review page shows progress. Sections with a query can be returned to the maker with a comment. "Support" is offered once every section is marked reviewed and no query is open. That last rule is applied by the screen; the workflow API itself accepts a support without marks.
- **Return.** The maker sees the returned sections and the query on each. Only returned sections and sections that depend on them can be changed; the rest stay as submitted. The maker confirms the changed sections, can reply to the reviewer, and resubmits. The reasons recorded with the last submission are offered again.
- **Second look.** A mark belongs to the version of the section it was made on. An unchanged section keeps its mark on resubmission; a changed section shows "Changed since your last review" with the earlier query.
- **Trail.** Every submit, return and support is listed with who did it, when and the comment.
- Marks record that a reviewer read a section. They are not a credit decision, and the screens say so. The Credit Approver role exists in the workflow but is not one of the two roles on the switch; after support, the checker can hand the ES on.

Code: `backend/app/services/review.py`, `GET /cases/{id}/review`, `POST /cases/{id}/review/marks`, `frontend/src/workbench/Review.jsx`.

## New information update (13 Nov 2026)

Specification: `docs/new_information_spec.md`. Code: `backend/app/es2/updates.py`, screen `frontend/src/workbench/Updates.jsx` ("What changed" in the rail).

- When a later document replaces an earlier one, the What changed page lists the new documents and every affected section: marked "Update required", or citing a replaced document.
- A section that reads another affected section waits for it. The order comes from what each version recorded it read, `uses_sections` and `reads_sections` in the specification, and the team dependency rules.
- A proposal is a full candidate version prepared by the drafting engine against the current documents and compared in Python. Nothing is saved to the section. It is one or more drafting calls, behind the live gate, recorded in the ledger.
- Figures: tables calculated by code and tables copied from sources are compared cell by cell and applied together. In copied tables, a text cell (remark, description) keeps its current wording unless that wording cites a replaced document. A row that is no longer sourced is flagged.
- Wording: only affected parts are proposed (cites a replaced document, uses a new document, draws on a changed section, refers to changed figures). The maker accepts or keeps each part. Other wording is kept as written.
- Applying saves a new version, carries analyst notes and added content, and resets confirmation. Kept wording that cites a replaced document is allowed but the section cannot be confirmed until it is updated.
- Endpoints: `GET /cases/{id}/sections/updates`, `POST /cases/{id}/sections/{n}/update-proposal`, `POST /cases/{id}/sections/update-proposals/{proposal}/apply` and `/dismiss`.
- Demo papers: `demo/synthetic_keppel/late_update/` (revised CAS, term sheet, projections and valuation, all fictional). On the Files screen, scan the "Late update" folder.
- Live result on the Keppel REIT case: 12 of 13 drafted sections affected, all updated in 15 calls for USD 13.77. ES after the update: `docs/demo/Keppel_REIT_ES_after_update.docx` and `.pdf`. Screens: `docs/screens/enh_19` to `enh_29`.
