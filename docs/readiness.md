# Expected inputs and section readiness (B05)

`GapService.refresh(case_id)` evaluates the **case's stored configuration snapshot**, not the current YAML. It upserts the 22 catalogue entries, including N/A entries with reasons, and applicable suggestions. `ReadinessService.refresh(case_id)` also persists all configured sections and returns `(gap_snapshot, sections)`. Upload, duplicate intake and folder scan call this refresh inside their existing transaction. Other services must refresh after confirmation, spread validation, dismissal, case-attribute or CA-position changes. Services never commit; API callers serialize SQLite writes with `BEGIN IMMEDIATE`.

API routes, using the same `create_app(sessions=..., storage_root=...)` setup as intake:

- `GET /cases/{case_id}/readiness`: expected documents with names and `satisfied`, all sections, and open requests grouped by `RM`, `client`, `internal team`. This refreshes derived records without searching, generating prose or calling providers.
- `GET /cases/{case_id}/request-list`: downloadable UTF-8 plain-text request list. Includes why, affected sections, mandatory/optional status, alternative groups, search outcome, manual-review/partial-public details and dismissal reason. This is not the template-filled ES Word export (B18).
- `POST /cases/{case_id}/expected-documents/{expected_id}/dismiss`: JSON `{ "actor": "demo-ca", "role": "CA", "reason": "Awaiting the RM" }`. A nonblank reason and actor are mandatory; role switching demonstrates process, not real authorization.
- `POST /cases/{case_id}/expected-documents/{expected_id}/restore`: same request shape; clears the active dismissal. Dismissal is current checklist state, not an append-only history. Versioned workflow events remain later work.

Document statuses are exactly **Provided**, **Found publicly**, **Can generate**, **Missing**, **Suggested**, **Not applicable**, **Dismissed**. Generated validated spreads use Provided; Can generate is only an offer. Non-catalogue suggestions retain Suggested even when contextual evidence is linked. Expected rows retain public-search attempts/outcomes across refresh; B05 never runs a search. The default outcome is **not run**, never an invented no-match result. Dismissed optional requests are hidden from the request list; dismissed mandatory inputs remain visible and unsatisfied until qualifying evidence arrives. Dismissal cannot act as a submission override.

Readiness states are exactly **Waiting for input**, **Can draft (partial)**, **Can draft (full)**, **Not applicable**, **Drafted**, **Stale**, **CA confirmed**. `completeness` (`none`, `partial`, `full`) and named `gaps` remain separate. Optional gaps can coexist with full readiness. Full means all applicable mandatory inputs/alternatives and dependencies are complete; it is not section confirmation or submission approval. An unconfirmed public find supports a partial draft but cannot satisfy a mandatory input. A financial report alternative closes the group, not unrelated ownership, property, conduct or rating inputs.

Synthesis waits until every applicable dependency has usable inputs, then inherits partial/full completeness. Section 14 also waits for a nonblank CA position. FIG draft gates require prior ES for renewal comparison (section 3), supplied internal rating (12) and account conduct evidence (13); these prevent an annual report/external release/covenant certificate from being mistaken for the missing baseline or repayment record. Gates and their rationale live in configuration. The configured 9→7/10, 11→3–10 and 14→mandatory dependency graph is unchanged.

Draft display uses the current draft's stored input fingerprint. Changed evidence or a stale dependency marks an existing draft Stale without altering its text, current/confirmed version pointers, editor revision, ES snapshots or workflow state. Unchanged drafts show Drafted or CA confirmed as appropriate. B13 still owns redraft/version creation, confirmation reset, approved-working-version handling and any additional invalidation relationships (including valuation effects on repayment). B11 owns the safeguard requiring CA confirmation before drafting an assertion that a facility is unsecured; lack of a security report never supplies that assertion here.

## Evidence contracts for B06/B09

Only matching-entity documents with conflict status `none` or `accepted`, not superseded by another eligible version, contribute. Pending/rejected/wrong-entity versions cannot close gaps. Pending files surface named review details. Original bytes and intake metadata remain immutable.

An internal evidence service can write `Document.intake.catalogue_support` at document creation as a list of `{ "id": 20, "coverage": "full", "pages": [229, 230, 231] }`. This maps page-bound secondary evidence from one report to another catalogue input. Positive physical page numbers and explicit `full`/`partial` coverage are required. Primary classification can carry `intake.coverage: partial`. These fields are deliberately **not accepted as upload hints**; the evidence-producing service must validate the pages, borrower, period, property scope and coverage. B08 will validate actual page citations. The original public URL/retrieval date and synthetic marker remain on the linked document.

Catalogue public-support rules cap coverage even if a mapping says full: valuation/lease summaries are partial only, external ratings cannot satisfy internal rating, and public evidence cannot support private-only types. Public financial/ownership documents become full only after document confirmation. A suggestion of an industry code also needs CA confirmation.

`generation` and `generation_inputs` in the catalogue configure spread/industry-code offers. A file labelled Financial spread never proves calculation validation. A `Spread` with `validation_status: valid` and current, eligible financial-source document IDs supplies the generated spread input. All public sources still need CA confirmation for full readiness; a spread referencing superseded inputs no longer qualifies. G1 tests use explicitly labelled saved mock outputs; this is not the B09 spreading implementation.

Suggestions use case predicates (`when`) or held document triggers (`trigger_catalogue_ids`), plus owner, affected sections and reason. Security/covenant requirements use supplied case attributes; B05 does not infer deal facts from free text. A provided prior-conditions document triggers a Suggested request for fulfilment evidence. The limits-extract suggestion asks the CA to check whether the CAS has an exposure table; it does not assert that a table is missing.

The existing catalogue owner groups take precedence over the illustrative demo narrative: pricing is routed to the internal team and projections to the RM (usual source Client or RM). Review these configurable defaults with FIG.

Optional B05 configuration keys are omitted from old snapshot serialization when absent, preserving pre-B05 configuration hashes. Existing cases are never silently upgraded to newly edited rules. New cases receive current configured generation/suggestion/gate rules.
